## Findings before correction

**OBSERVED (owner report):** In code 5, on the card **«La tua programmazione è attiva» / "Your schedule is active"**, a large empty block remained between the description and the red **DISATTIVA / DEACTIVATE** button. The owner verified this visually on the phone and supplied no handset model, OS build or recording. This is a reported visual defect, not an agent device measurement.

**PROVEN (baseline source):** `StableFilterStatus()` composed **all five** `FilterStatus` alternatives as hidden children of a `Layout` driven by `stableContentMeasurePolicy(status.ordinal)`, which measured every alternative and reported `constraints.constrainHeight(alternatives.maxOf { it.height })`. The card therefore permanently reserved the tallest alternative — `SESSION_PAUSED`, whose `session_paused_detail` is the longest sentence in the set — even while the short `ACTIVE` copy was on screen, and the central button was pushed down by that reserved, invisible height. The same policy also backed both master-button labels, where the reservation covers only two short strings.

**PROVEN (baseline source):** `filterStatus()` returned the transient `SAVING` state whenever `busy` was true, replacing the card title and detail with `state_saving` / `saving_detail`. `SettingsStore.beginUpdate()` publishes `sessionPaused = true` synchronously at the start of every save and only `save()`'s success branch publishes `false`, so each save produced two additional card-copy changes beyond the transient `SAVING` text itself.

**INFERRED:** Removing the maximum-height reservation and keeping the committed copy on screen during a save eliminates the reported empty block without restoring the code-4 flicker, whose sources (a busy-conditional row inserted into the scrolling `Column`, and card copy of a differing length) are both addressed. **EVIDENCE_FOR:** the reservation and the transient copy are directly visible in the baseline source; the code-5 progress strip already sits outside the scrolling `Column` in a permanent four-dp overlay and is retained unchanged. **EVIDENCE_AGAINST:** no frame trace or real-device geometry was recorded for code 5 or code 6. **ALTERNATIVE_EXPLANATIONS:** OEM rendering, font shaping, keyboard/dialog transitions, legitimate list growth or scroll-range clamping may still contribute to perceived movement. **CONFIDENCE:** high for the source-level cause of the empty block; its complete contribution to what the owner saw remains unverified. **MINIMAL_DISCRIMINATING_EXPERIMENT:** compare the gap above **DEACTIVATE** in the `ACTIVE` state, and repeated identical saves at a fixed scroll offset, before and after the update on the owner's phone.

No configured AVD or SDK system image and no instrumented UI-test source set exist locally. No dependency or emulator image was added to manufacture cosmetic evidence. `adb` was started for read-only enumeration only: **no device was attached**, so no installation, role, permission, contact, call or device-setting action was performed.

## Correction and scope

- `StableFilterStatus` is replaced by `FilterStatusText`: a plain `Column` that composes **only** the visible state's title and detail. There is no `Layout`, no measure policy, no fixed height, no `minHeight`, no artificial padding and no truncation. The card height is whatever Compose derives from the available width, the locale and the font scale, so the button follows the description at the same 10-dp interval every other card on the screen uses.
- `FilterStatus.SAVING` and the `saving` parameter of `filterStatus()` are removed. The four remaining entries — `OFF`, `ACTIVE`, `SESSION_PAUSED`, `SETUP_REQUIRED` — are all real committed conditions with distinguishable copy, and their relative precedence is unchanged.
- A new two-line `cardStatus(committed, busy, held)` separates the confirmed state from the transient save. `Home` computes `committed` from one observable sample, holds it in a `remember`ed value refreshed by `SideEffect { if (!busy) held = committed }`, and shows `held` while `busy`. A save therefore never swaps the card description for temporary text of a different length, and only completion can change it. `held` can only initialize while `busy` is false, because every control that sets `busy` lives in the same branch.
- The save feedback stays where code 5 put it: the permanent four-dp overlay strip outside the scrolling `Column`, so no child is inserted or removed and the column geometry never changes. Its polite live region now announces `saving_detail` — "Filtering is temporarily paused while your changes are saved." — instead of the shorter `state_saving`, so the autonomous feedback states the real temporary pause rather than only the operation name. `state_saving` became unused and was deleted from both locales; no other string was added, removed or reworded.
- The master button is untouched: `heightIn(min = 64.dp)`, `contentPadding`, the committed red/green colours, the steady disabled colours while busy, the `!busy` enable condition and the synchronous `if (busy) return` guard in `persist()` all remain. `stableContentMeasurePolicy` is deliberately **retained** for `StableMasterButtonLabel`, where reserving the natural maximum of two short labels prevents a button-height jump when only the longer translated label wraps at a large font scale. Its documentation now records that it must not be applied to status text.
- Nothing else moved. `rememberScrollState`, the persistence ordering, the edit-control disabling, the Material 3 error dialog and the contact picker are unchanged. A legitimate `ACTIVE` ↔ `OFF` transition may still change the number of description lines and resize the card naturally; that is a committed content change, not a transient one.

**PROVEN (compiled-input hashes):** 8 of the 32 hashed build inputs changed — `app/build.gradle.kts` (version code only), `FilterStatus.kt`, `MainActivity.kt`, `StableContentLayout.kt` (documentation comment only), both `strings.xml`, and the two rewritten test files. `ScreeningService.kt`, `SettingsStore.kt`, `SettingsCodec.kt`, `Rules.kt`, `ContactPicking.kt`, `NumberEntry.kt`, `ScreeningAccess.kt`, `AndroidManifest.xml`, `themes.xml`, `data_extraction_rules.xml`, `gradle.lockfile`, the Gradle wrapper and the root build scripts are **byte-identical to code 5**. Matching, weekly rules, time-zone handling, permissions and the fail-open strategy are untouched; persistence and the data shape are untouched. The four protected canonical files (`START.md`, `AGENTS.md`, `ROADMAP.md`, `CORROBORATIONS.md`) were not modified. No key was generated, rotated, copied or committed. There is no data migration or clearing, so candidates 1–5 update in place with their settings preserved.

**Documentation:** `docs/PRODUCT_SPEC.md` R6 now owns the corrected behavior — the status card occupies only the natural height of the state actually visible, saving inserts no transient row and swaps no card copy, and progress plus the real temporary pause are reported by an accessible non-displacing indicator while the card keeps the committed state. `docs/BUILD.md` and `tests/TEST_MATRIX.md` point at this run. Earlier receipts under `evidence/runs/` are preserved unmodified.

## Verification

**PROVEN:** All **67 JVM tests pass**, zero failures, zero errors, zero skips. The 62 pre-code-5 tests are retained unchanged, including screening, schedule/DST, codec, number validation, contact picking and the issue #1 and issue #2 regressions.

The four code-5 layout tests were dispositioned per the new specification rather than left to crystallize the defect: the master-label test is kept and extended with placement assertions; the natural-growth and parent-constraint tests are retargeted to the button labels, which are the policy's only remaining consumers; and the two tests that asserted an identical maximum height for every status — including one fixed 150-px expectation — were removed, because that assertion *is* the reported defect. Two tests were added to `FilterStatusTest`:

1. `theCardOnlyOffersRealCommittedStatesWithDistinguishableCopy` — the enum is exactly the four real committed states, no two share both title and detail, and the transient saving sentence is not part of any card state.
2. `anInFlightSaveNeverReplacesTheCommittedCardCopy` — drives the production `filterStatus`/`cardStatus` pair with the **real** `SettingsStore.sessionPauseFlow` publisher across save, toggle-to-OFF, re-activate, failed save and retry, asserting that an in-flight save never swaps the copy, that only completion changes the committed state, that a failure surfaces the genuine `SESSION_PAUSED`, and that a retry never flashes `ACTIVE`.

`observedPauseClearsAfterBackgroundCompletionWithoutSettingsChangeOrResume` and `repeatedSavesFailureAndRetryKeepPublishedStateInSync` are retained against the new signature, so the issue #1 observable-pause bridge and the publisher/revision invariants stay covered.

**LIMIT:** These tests are synthetic. They exercise the real measurement policy with controlled child dimensions and the real pause publisher, but they do not shape Android text, compose or render the `Home` screen, run TalkBack, scroll a real surface, inject a real IO error, or prove the absence of perceived flicker. The natural height of the visible status text is now **structural** — a plain `Column` with a single state — and has no JVM proof at all; only the owner's phone can confirm it. `anInFlightSaveNeverReplacesTheCommittedCardCopy` reproduces `Home`'s hold/`SideEffect` rule by hand, so the simulation could drift from the real composition, and the assumption that no frame observes `busy == false` with a stale pause after a successful save rests on main-thread dispatcher FIFO ordering that is not JVM-testable. No emulator, instrumented harness or test dependency was added to close these gaps.

**Recorded limitations the owner must explicitly accept or request as a follow-up:**

- *Completion is not announced.* Code 5 changed the card's polite live region from the saving copy to the final state, so TalkBack announced completion. With the card frozen, a save that does not change the committed state — editing a window or a number while `ACTIVE` — announces the start and then nothing. No completion announcer was added: it needs new localized strings and a mechanism whose behavior on TalkBack/OEM builds cannot be verified here, which would exceed a small presentation-only change.
- *The pause sentence is audible but not visible.* The temporary-pause statement now travels as the strip's `contentDescription` on a four-dp bar, so a low-vision user who does not run a screen reader has no readable pause text during the write. This is what the non-displacing-feedback requirement asks for, and the pause spans one small atomic file write; enlarging the overlay to show text would cover scrolled content and reintroduce a transient visual change.
